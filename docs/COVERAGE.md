# Coverage: how "99%" is measured

Sparagmos の目標は「Rust 1.100.0 を 99% のレベルで実行できること」です。
この文書は、その 99% を構成する4つの指標の定義と現在の実測値を記述します。
過去の測定履歴は git の履歴と GitHub Issues にあり、この文書には書きません。

達成条件は4指標すべてが 99% 以上であることです。指標同士を混ぜた単一の
数値は作りません。

| 指標 | 現在値 |
|---|---|
| 1. MIR バリアント網羅率 | 77.5% (実装済み 31 / 母数 40) |
| 2(a). 自前コーパスのパス率 | 100% (47 / 47) |
| 2(b). rustc テストスイート部分集合のパス率 | 88.483% (パス 22,065 / 母数 24,937 の全母数換算) |
| 2(c). rustc 自体の実行 | 未着手 |
| 参考. コーパスの JIT 経路パス率 | 100% (47 / 47) |
| 3. std 機能網羅率 | 97.826% (1,710 / 1,748) |
| 4. テストスイート全体の JIT パス率 | 69.535% (17,340 / 24,937) |

現在の実測値は、Official Measurement run 46043193970 (main ヘッド
`916dc044`) の結果です。指標2(b) は今回、母数 24,937 件の全件を
判定できました (詳細は指標2(b) の節)。

## 指標1: MIR バリアント網羅率

### 母数

rust-lang/rust のタグ `1.100.0` の
`compiler/rustc_middle/src/mir/syntax.rs` から機械的に数えた
`StatementKind` (12) + `TerminatorKind` (15) + `Rvalue` (13) = **40** です。
手で選んだ数ではありません。

### 「実装済み」の判定

ドライバ (Stable MIR からの変換) に変換アームが存在し、かつ意味テストが
インタプリタで通ること。JIT がそのバリアントを主張する場合は JIT でも
テストが通ること。

### 現在の内訳

| enum | 実装済み | 到達不能 | 未対応 |
|---|---|---|---|
| StatementKind (12) | 11 | 1 | 0 |
| TerminatorKind (15) | 8 | 7 | 0 |
| Rvalue (13) | 12 | 1 | 0 |
| 合計 (40) | **31** | **9** | **0** |

### 到達不能 (9)

以下の9バリアントは Stable MIR (`rustc_public` 1.100.0) に存在しないため、
ドライバの境界に到達し得ません。実装済みには数えず、独立の区分として
数えます。

- StatementKind: `BackwardIncompatibleDropHint`
- TerminatorKind: `UnwindResume`, `UnwindTerminate`, `TailCall`, `Yield`,
  `CoroutineDrop`, `FalseEdge`, `FalseUnwind`
- Rvalue: `WrapUnsafeBinder`

### ThreadLocalRef

Rvalue `ThreadLocalRef` は実装済みです。ドライバがスレッドローカル
static の宣言型と初期化子をプログラムテーブルに記録し、インタプリタは
スレッドごとのストレージを初回アクセス時にその初期化子で seed します。
スレッド終了時のデストラクタは実行しません (std のセマンティクスとの
差異として明記します)。

### InlineAsm の範囲

`InlineAsm` は実装済みに数えます。実行できるのは、レジスタ完結型の
プログラム (対象 mnemonic のみで構成され、プレースホルダ operand と
整数即値だけを使うテンプレート)、step-over クラス、および naked な
`ret` です。範囲外の要素を含むテンプレートは全体が明示的エラーに
なります。

## 指標2: テストパス率

### 2(a) 自前コーパス

`tests/corpus` の **47 / 47 (100%)**。`sparagmos corpus` で測定します。

### 2(b) rustc テストスイート部分集合

#### 母数

rust-lang/rust タグ `1.100.0` のテストスイート全体から機械的に抽出した
**24,937** 件です (抽出 24,940 件から、環境依存の run-make-cargo テスト
3件 `thumb-none-qemu` / `uefi-qemu` / `x86_64-fortanix-unknown-sgx-lvi`
のみを個別に除外)。単一ファイルに収まるテストだけに絞ることはしません。
FFI を含むテスト、補助ファイルやビルドステップを要するテストも母数に
含み、実行できないテストは分母から外さず失敗として数えます。

判定種別ごとの内訳:

| 判定種別 | 件数 | 判定済み | 現在のパス |
|---|---|---|---|
| 実行 (exec) | 4,149 | 4,149 | 3,933 (94.794%) |
| コンパイル時検証 (compile-check) | 18,332 | 18,332 | 17,901 (97.649%) |
| 手順 (procedure / run-make) | 551 | 551 | 90 (16.334%) |
| デバッガ実行 (exec-debugger) | 170 | 170 | 141 (82.941%) |
| rustdoc 検証 | 1,735 | 1,735 | 0 |
| 合計 | 24,937 | 24,937 | **22,065** |

パス率は全母数換算で **88.483%** (22,065 / 24,937) です。パスして
いないのは 2,872 件で、全て判定済みの失敗です (種別ごとの残りは、
実行 216、コンパイル時検証 431、rustdoc 検証 1,735、手順 461、
デバッガ実行 29)。

#### Windows クラスの判定について

Windows 両クラス (windows-msvc 72 件、windows-gnu 9 件、計 81 件)
は、ネイティブの Windows ランナー上でビルドしたドライバで判定して
います。今回の計測では 81 件すべてを判定できました。そのうち
windows-gnu の次の 4 件は失敗として判定されています:
`tests/run-make/mingw-export-call-convention`、
`tests/run-make/raw-dylib-custom-dlltool`、
`tests/run-make/windows-gnu-corrupt-drective` (いずれも手順、
stage-3 のサポートビルド失敗) と
`tests/ui/linkage-attr/raw-dylib/windows/dlltool-failed.rs`
(コンパイル時検証、失敗すべきテストでの compiler crash) です。

前回の確定値 (run 46028839415) と両方で判定できた範囲の差分は
gain 41 / loss 77 です。loss の主体は実装の退行ではありません。
loss 77 件のうち 74 件は `tests/crashes/` 配下のレコードで、

gain のうち帰属が確定しているのは 17 件です: PR #908 が 8 件
(`tests/ui-fulldeps/internal-lints/` 配下の 4 件
`direct-use-of-rustc-type-ir.rs`、`import-of-type-ir-inherent.rs`、
`import-of-type-ir-traits.rs`、
`non_glob_import_of_type_ir_inherent.rs`、
`tests/ui/lifetimes/issue-91763.rs`、
`tests/ui/lint/redundant-semicolon/redundant-semi-proc-macro.rs`、
`tests/ui/suggestions/issue-61963.rs`、
`tests/ui/traits/next-solver/overflow/recursion-limit-zero-issue-115351.rs`)、
PR #909 が 1 件 (`tests/run-make/prefer-rlib`、手順)、PR #889 が
2 件 (`tests/ui/panics/issue-47429-short-backtraces.rs`、

残る gain 24 件のうち 23 件は機構と整合するもの
(symbol-names 系の判定クラスタ 18 件、by-ref 定数 2 件、
手順 3 件) で、1 件は帰属なしです。

loss の残り 3 件のうち 1 件は
`tests/ui/recursion/recursion_limit/zero-overflow.rs`

ために失敗します。根因のギャップは Issue #509 に記録済みです。
残る 2 件 (`tests/ui/imports/ambiguous-reachable.rs`、
コンパイル時検証、`tests/ui/impl-trait/example-calendar.rs`、
実行) は帰属が判明しておらず、トリアージ中です。

#### パスの定義

- 実行系: プログラムを実行し、終了コードと標準出力を期待値と比較します。
- コンパイル時検証系: コンパイルの成否 (成功すべきテストは変換が成功し、
  失敗すべきテストはコンパイルが失敗する) の一致で判定します。
  `.stderr` 注釈や FileCheck との照合は実装していません。
  `-Zunpretty` や `--print` のように、出力そのものが判定対象で
  コンパイルの成否では決まらないレコードは、変換を試行せず
  失敗として数えます。
  単相化されず、どのプログラムからも要求されなかった generic 定義は
  変換されたとは数えません (pass に数えると過大申告になるため)。
  ただし、要求されなかったデータコンストラクタと自明な定数は、本体を
  持たず使用箇所に値が埋め込まれるため変換済みとして数え、その件数は
  変換レポートに「本体なしで変換済み」として別行で記録されます。
- デバッガ実行系: ハーネスがデバッガセッションの期待出力を解釈して
  判定します。
- 手順系: レシピ (run-make) を実行し、生成物との照合で判定します。
- rustdoc 系: 生成物 (レンダリング済みドキュメント) との照合で決まります。
  公式計測では rustdoc 成果物ツリーのキャッシュがまだ用意されて
  いないため、オラクルを通過したレコードは未試行として記録され、
  パスしません。
  rustdoc 検証 (1,735 件) が未試行のままである限り、全体の上限は
  93.04% です。

- 環境適用性 (全種別共通): `only-*` / `ignore-*` / `needs-*`
  ディレクティブは、参照環境 (ホストターゲット
  x86_64-unknown-linux-gnu と、ピン留めした公式リリース
  1.100.0 ツールチェン。チャネルは stable、リリースビルド構成)
  に対して compiletest と同じ方法で評価します。条件が
  満たされないレコードは試行せず、失敗として数えます
  (バケット「環境外」)。満たされない前提は参照環境の属性
  そのもの (他ターゲット、nightly チャネル、debug assertions /
  Enzyme / offload を有効化した rustc ビルド、ホスト
  ターゲットの未対応サニタイザ等) であるため、公式計測の
  CI 環境でも同一に満たされません。

### 2(c) rustc 自体

未着手です。指標1・2(b)・3 が 99% に達してから開始します。

### 参考: コーパスの JIT 経路パス率

自前コーパス 47 件を JIT 経路で実行した参考値です (指標4とは別物で、
達成条件には含みません)。現在 **47 / 47 (100%)** で、誤結果は 0 件です。JIT 経路にはインタプリタと同じ
名前解決を持つビルトイン層 (fmt 機械を含む) があり、本体なし呼び出しは
そちらへ委譲されます。定数はプログラム所有の静的ブロブとして実体化され、
3ワード以上の引数と sret 規約の戻り値、配列の集約も扱えます。配列の
by-value 反復 (IntoIter) も要素型ごとのレイアウトで実行できます。
プログラムに含まれない呼び出しは、到達した時点で同じ文言で失敗する
トラップとして下げられます (インタプリタが実行時に初めてエラーを出す
意味論と一致)。128ビット整数は
ワードペアとして実行できます。

## 指標3: std 機能網羅率

### 母数

出現ベースで定義します。指標2のプログラム群 (自前コーパス + テスト
部分集合の stage-1 候補) の変換済み MIR に実際に呼び出し先として現れる
`std` / `core` / `alloc` の関数パスの集合が母数です。現在 **1,748** 件。
変換できるプログラムが増えると現れるパスも増えるため、母数は測定ごとに
動き得ます。

### 「網羅」の判定

あるパスへの呼び出しがインタプリタで実行可能であること。すなわち、
変換済みプログラムにその関数の本体が含まれるか、インタプリタの
ビルトインとして解決できること。現在 **1,710 / 1,748 (97.826%)**。
全プログラムで本体が揃うことを要求する厳密値では 1,694 / 1,748 (96.911%)
です。母数は、PR #937 の計測条件変更 (measure-host ジョブへの
全ターゲット導入) により前回から 38 件増えました。共通する
1,710 項目の flip は上下とも 0 件で、新規 38 件のうち 33 件は
既に実行可能です。

## 指標4: テストスイート全体の JIT パス率

### 母数

指標2(b) と同じ **24,937** 件です。未対応のレコードも母数から
外さず、fail として数えます。

### 「パス」の定義

実行系のレコードは JIT 実行で判定します (判定基準は指標2(b) の
ランナーと同じで、JIT が名前付き未対応を返したものは fail です)。
コンパイル検査系のレコードは、変換の成否が期待と一致することに
加えて、プログラム全体の JIT ロワリングが成功することを要求します。
procedure / exec-debugger / rustdoc のレコードは現在 JIT 経路では
試行しておらず、fail として数えます。

### 現在値

**17,340 / 24,937 (69.535%)**。内訳はコンパイル時検証
15,908 / 18,332、実行 1,432 / 4,149 で、procedure / exec-debugger /
rustdoc の nature は 0 件です。前回の確定値 (run 46028839415) との
差分は gain 39 / loss 87 で、loss のうち 74 件は PR #920 の
再分類によるものです。主な失敗要因は、JIT ロワリング未対応 (その他) と、
変換済み本体を持たない関数への呼び出しです。この値は、未対応の
呼び出しを到達時点で失敗するトラップとして下げ、String をヒープ
機構で処理する現在の jit-compile の意味論のもとで測ったものです。

JIT 化の実装作業は、指標1・2・3 が 99% に達してから行います。
それまでは計測とベースライン報告のみです。

## 現在の制限

実行モデルとカバレッジに影響する、現在の制限をまとめます。

- フラットなバイトアドレスメモリを持ちません。参照は値のツリーへの
  パスで表現されます。このため `UnsafeCell::get()` のような生ポインタ
  経由のアクセスの一部形状は、ポインタ先のスカラではなく ADT 全体を
  返します。
- ファイルシステムと環境変数の読み取りはモデル化していません。
  コマンドライン引数、標準出力・標準エラー、プロセス終了、時刻、
  スレッド (協調スケジューリング) はモデル化しています。
- `static` のストレージはありますが、static の内部へのファット参照
  (`str` / スライス) はスナップショットとして復号され、enum ペイロード
  内への射影は計算しません。
- 死んだ言及からのみ要求される定数 (rustc の required-consts) の失敗は、
  最適化前 MIR へ単相化コレクタを再生する検査でコンパイル判定モードに
  おいて検出します。インスタンス化自体の再帰上限で失敗するケースは
  この検査の対象外です。
- union のフィールドをまたぐ型のパニング読み取り (意図的な
  type punning) は未対応です。
- 非同期処理は実際の `Waker` 構築を伴う形状では `RawWaker` の
  transmute で止まります。コルーチンの状態オブジェクト自体は実行
  できます。
- 非同期クロージャ (`ty::CoroutineClosure`) の変換は `rustc_public`
  1.100.0 側で未実装のため、その本体を含むテストは変換できません。
- JIT の未対応 (いずれも明示的エラー): `&dyn` トレイト
  オブジェクト、ThreadLocalRef、実命令を含む InlineAsm。
- パターンマッチの機械 (`Pattern` 関連) はモデル化していません。

## 測定の規律

- 公式値は、統合済みの main に対する combined 測定でのみ更新します。
- 公式計測のドライバは `measure` プロファイル (最適化あり、dev
  プロファイルの debug assertions と overflow checks は維持) で
  ビルドします。これはレコードの実行速度だけを変えるため、
  タイムアウト境界付近のレコードの成否が変わり得ます。切り替え
  前後の公式値は同条件の時系列ではありません。
- 測定コマンド:
  - コーパス: `./target/debug/sparagmos corpus`
  - 指標1: `python3 scripts/variant-matrix.py --out <path>`
  - 指標2(b): `python3 scripts/rustc-subset-run.py --survey-json <survey>
    --rust-dir <rust-1.100.0 checkout> --driver-bin <sparagmos-driver>
    --out <path>`
  - 指標3: `python3 scripts/std-coverage.py --results-json <指標2(b)の結果>
    --rust-dir <checkout> --driver-bin <sparagmos-driver> --out <path>`
  - 指標4: 指標2(b) のコマンドに `--jit` を付けたもの (ドライバの
    `run-jit` / `jit-compile` モードで判定します)
- 未対応の項目は、黙って落とさず常に名前付きの明示的エラーにします。
